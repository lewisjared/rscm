# Documenting Components

This guide explains how to write documentation for RSCM components so they appear correctly in the generated documentation site.

## Overview

Component documentation is generated from two sources:

- **Rust components**: JSON metadata files in `docs/component_metadata/`, generated by the `rscm-doc-gen` crate which parses Rust source files
- **Python components**: Extracted from the `Component` class registry via docstrings and type annotations

`rscm-doc-gen` finds every struct that derives `ComponentIO`,
in the crates listed in the `docs-metadata` Makefile target.
These are currently `rscm-components`, `rscm-two-layer` and `rscm-magicc`.
Components in a new crate only appear once the crate is added to that target.
Components that implement `Component` by hand get no page.
In `rscm-magicc` these are `HalocarbonChemistry`, `OzoneForcing` and `ForcingAggregation`.

The `docs/gen_doc_stubs.py` script combines both sources and generates markdown pages for each component.

## Rust Components

### Docstrings

Write documentation in the module docs (`//!`) of the component's file and the struct docs (`///`).
The page shows the module's introduction, then the struct's, then the sections of each.
A one-line first paragraph is a title.
The page drops the module's title, and the struct's too when the module has docs,
because the page heading names the component.

```rust
/// CO2 effective radiative forcing component
///
/// Computes ERF using the standard logarithmic relationship:
///
/// $$
/// ERF = \frac{ERF_{2 \times CO_2}}{\ln(2)} \cdot \ln\left(\frac{C}{C_0}\right)
/// $$
///
/// where:
///
/// - $C$ is the current atmospheric CO2 concentration
/// - $C_0$ is the pre-industrial concentration
/// - $ERF_{2 \times CO_2}$ is the forcing from a doubling of CO2
#[derive(Debug, Serialize, Deserialize, ComponentIO)]
#[component(tags = ["radiative-forcing", "co2", "simple", "stable"], category = "Radiative Forcing")]
#[inputs(
    concentration { name = "Atmospheric Concentrations|CO2", unit = "ppm" },
)]
#[outputs(
    erf { name = "Effective Radiative Forcing|CO2", unit = "W/m^2" },
)]
pub struct CO2Erf {
    parameters: CO2ErfParameters,
}
```

### Equations

Use KaTeX syntax for mathematical equations:

- **Inline**: `$x^2$` renders as $x^2$
- **Block**: Use `$$` delimiters on separate lines for display equations

The documentation site renders KaTeX automatically.

### Markdown

`gen_doc_stubs.py` normalises the doc comments before Python-Markdown renders them,
so rustdoc conventions work:

- `#` headings become sections one level below the page title.
- `# Inputs`, `# Outputs` and `# States` sections are removed.
  A bullet that names a declared variable in backticks becomes its description in the table.
  The other bullets are listed under the table.
- Lists get the blank line before them and the four-space nesting that Python-Markdown needs.
- `$$` blocks and tables get blank lines around them.
- Intra-doc links such as ``[`TwoLayerParameters`]`` become code,
  and `[text](crate::path)` becomes plain text.

A `Units:` line in a parameter's doc comment fills the Unit column of the parameters table.

### Component Metadata

`rscm-doc-gen` writes one JSON file per component.
`ComponentDocMetadata` in `crates/rscm-doc-gen/src/schema.rs` defines the fields:

| Field                                | Content                                          |
| ------------------------------------ | ------------------------------------------------ |
| `name`, `module_path`, `source_file` | Where the component struct is defined            |
| `description`                        | The combined doc comments                        |
| `category`, `tags`                   | From the `#[component(...)]` attribute           |
| `inputs`, `outputs`, `states`        | Variable name, unit and grid for each IO field   |
| `parameters`                         | Name, type and doc comment for each parameter    |

### Parameters

Parameters are read from the fields of the component's `*Parameters` struct.
The struct must be defined in the same source file as the component.
Doc comments on its fields become the parameter descriptions.
MAGICC components keep their parameter structs in `rscm_magicc::parameters`,
so their pages currently have no parameters table.

### Generating Metadata

Run the doc-gen tool to update metadata files:

```bash
make docs-metadata
```

This parses the component source files and writes JSON to `docs/component_metadata/`.
Commit the regenerated JSON files with the component change.

### Category and Tags

Set the category and tags with the `#[component(...)]` attribute shown above.
Do not edit the JSON files by hand, because `make docs-metadata` overwrites them.
Components group by category on the index page, and a component without one is listed under "Other".
Reuse an existing category where one fits:

| Category              | Description                                 |
| --------------------- | ------------------------------------------- |
| Atmospheric Chemistry | Gas cycles and lifetimes (CH4, N2O)         |
| Carbon Cycle          | CO2 emissions, concentrations, uptake       |
| Climate               | Temperature response to forcing             |
| Ocean                 | Ocean heat uptake and dynamics              |
| Ocean Carbon Cycle    | Ocean carbonate chemistry                   |
| Radiative Forcing     | Radiative forcing calculations              |
| Temperature           | Simple temperature models such as TwoLayer  |

Common tags: `stable`, `experimental`, `simple`, `magicc`, `carbon-cycle`, `forcing`, `ocean`

## Python Components

### Docstrings

For Python components, the description comes from the class docstring,
and the parameters from the `__init__` docstring.
As for Rust, the page drops a one-line title paragraph.

```python
class SimpleEmissionsToConcentration(Component):
    r"""
    Simple emissions to concentration component.

    Converts CO2 emissions to atmospheric concentration changes using
    a linear airborne fraction model:

    $$
    C(t) = C(t-1) + \alpha \cdot E(t) \cdot \frac{M_{CO2}}{M_C}
    $$

    where $\alpha$ is the airborne fraction (fraction of emissions
    remaining in the atmosphere).
    """

    emissions = Input("Emissions|CO2", unit="GtCO2")
    concentration = State("Atmospheric Concentrations|CO2", unit="ppm")

    def __init__(self, airborne_fraction: float, gtc_to_ppm: float):
        """
        Parameters
        ----------
        airborne_fraction
            Fraction of emissions remaining in atmosphere (typically ~0.45)
        gtc_to_ppm
            Conversion factor from GtC to ppm (~0.47 ppm/GtC)
        """
        self.airborne_fraction = airborne_fraction
        self.gtc_to_ppm = gtc_to_ppm
```

### Registration

Python components are automatically registered when their class is defined.
The docs build only imports `rscm.example_components`.
Components in other modules appear only once `load_python_components()` imports them.
To exclude a component from documentation (e.g., abstract base classes):

```python
class AbstractComponent(Component, register=False):
    """This won't appear in the component index."""
    pass
```

### Parameter Documentation

Document parameters in the `__init__` docstring using numpy-style formatting:

```python
def __init__(self, tau: float, sensitivity: float):
    """
    Parameters
    ----------
    tau
        Time constant for the exponential decay (years)
    sensitivity
        Climate sensitivity parameter (K per W/m^2)
    """
```

## Generated Documentation

Each component page includes:

1. **Header**: Name, category, tags, language
2. **Description**: The doc comments, with rendered equations
3. **Inputs table**: Variable name, unit, grid type and any description from `# Inputs`
4. **Outputs table**: The same for outputs
5. **States table**: (if applicable) The same for state variables
6. **Parameters table**: Name, type, unit and description of each parameter
7. **Usage examples**: Python and Rust code snippets.
   The Python snippet needs a `<Name>Builder` in `rscm.components`, `rscm.two_layer` or `rscm.magicc`.
8. **Source reference**: Path to the source file

## Building Documentation

Preview the documentation site locally:

```bash
# Serve locally with auto-reload
make docs-serve

# Build static site
make docs
```

Both targets rebuild the extension and regenerate the component metadata first.
They use the `docs` dependency group, so no separate install step is needed.

The generated component pages appear under `site/components/`.

## Best Practices

### Writing Effective Descriptions

- Start with a one-line title, then a sentence saying what the component does.
  The index page uses that sentence as the component's summary.
- Explain the physical/mathematical basis
- Include the governing equations with variable definitions
- Note any assumptions or limitations

### Variable Naming

Follow the hierarchical naming convention:

- `Emissions|CO2` - CO2 emissions
- `Atmospheric Concentrations|CO2` - Atmospheric CO2 concentration
- `Effective Radiative Forcing|CO2` - ERF from CO2
- `Surface Air Temperature Change` - Global mean surface temperature

### Units

Use unit strings that `rscm.core.Unit` can parse:

- `GtCO2`, `GtC` - Gigatonnes of CO2 or carbon
- `ppm` - Parts per million
- `W/m^2` - Watts per square metre
- `K` - Kelvin
- `yr` - Years

### Equations

- Define all variables used in equations
- Use consistent notation across related components
- Reference literature sources where applicable

### Keeping Documentation Updated

1. Update docstrings when component behaviour changes
2. Re-run `make docs-metadata` after modifying Rust components
3. Verify changes with `make docs-serve` before committing

`make docs` and `make docs-serve` run step 2 automatically.
